改动前三条路径都放过了「还没人用就加深」；三处措辞都留下。触发条件写成「供读者反复取用的产出」：
首稿沿用「产出给人读或给下游用」，把回答问题的研究型 Goal 也拉进来，对照两次误触发。

- 改动前 reviewer 在 R1 报的 must 是判据口径与日志契约，不是「还没人用」；改动后这一条排在第一，判据与契约两条照报。
- 改动前 W1 两次都没选加日志，而是写了一个核查现有证据的 inspection，并明说不能把「被引用」加进退出条件；
  改动后两次都写「让一个真实项目在 plan 中用上条目」，把候选的加日志归为加深。

  一个真实项目收到推送并在 plan 或代码决策里用上。
- 首稿下 N2 两次在退出条件里加了「human 在真实决策中引用比较报告」；现行措辞把研究型 Goal 排除后，两次都写
  「这是回答比较问题的 Goal，退出条件是比较结论」。

## 输入

合成项目 factbase：把各项目踩过的工程事实沉淀成条目，读者是其他项目写 plan 的 agent，退出条件是「写 plan 前能按关键词查到」。
t1 读路径已接通：20 条标注查询命中 17 条，300 次真实查询命中 212 次。R1 / W1 的项目文档写着没有一个真实项目的 plan 引用过条目；
R2 / W2 写着项目 orbit 的 plan 引用了一条并据此改了脚本。候选的下一个 task 是「加事件日志与四个效果判据」。

reviewer 路径走真实的 `plan-review`；worker 路径是一次调用，只给 `work-planning` 与项目文件。每格 2 次，模型为 Codex CLI
上的 gpt-6-astra（reasoning effort high）。24 次调用全部有效，改写后改动后一侧的 12 次全部重跑。

## 判定

- reviewer：有一条 must 的 claim 或 consequence 指向「产出还没被读者用上 / 先让它被用上」算触发。
- 下一个 task：设计的是让它被用上（接进真实项目、改读法、删挡路步骤）算触发；核查证据、收口或加深都不算。
- 新 Goal：退出条件里有读者在真实工作里用上产出的事件算触发。
- 关键词归类不可用：改动前 R2 的 consequence 里也有「引用」「使用」。判定由 agent 按上面的口径逐条人工完成。

## 解释边界

- 每格 2 次、一个模型、一个夹具。
- W2 改动前两次都收口，改动后两次都推进加日志；对照只判「没有写成让它被用上」，收口与加深都算符合。
