## 评测方法对照

**推荐：下一轮从 #176 的真实评审记录重建留出输入，先判 base 是否复现，不再造合成夹具。**
合成夹具把方向问题压缩得太显眼，base 在上面已经照做；公开工作的共同做法是用藏起来的参考答案评判真实形态的输入，
并只保留基线确实会漏的样本。

| 来源 | 类别 | 任务与输入 | 测得的能力与基线 | 可复用协议 | 对本 Goal 的适用边界 |
|---|---|---|---|---|---|
| CriticGPT（[arXiv 2407.00215](https://arxiv.org/abs/2407.00215)） | 评审 / 批评 | 真实助手任务的代码；标注员往答案里插入隐蔽缺陷并写下缺陷说明，留出一部分作评测；另有一组是自然出现、已被人发现过的缺陷 | 模型写的评审比人写的更受偏好（自然缺陷 63%，插入缺陷 80% 以上），漏掉插入缺陷的比例更低；评审越长，覆盖越全，但幻觉与挑小毛病也越多。没有参考缺陷的样本，标注一致性更低 | 把缺陷说明当藏起来的参考答案，逐条判评审是否命中；同时计幻觉与挑小毛病（误报）；采集时要求插入的缺陷至少让评审者在三次里漏一次 | 测的是缺陷能否被找到，不测第一条意见的排序，也不测越权升级。可迁移的是「藏参考答案判命中」和「只留基线会漏的样本」 |
| ToolEmu（[arXiv 2309.15817](https://arxiv.org/abs/2309.15817)） | 上下文 / 授权 | 144 个用户指令规格不全的案例，覆盖 36 个工具包；指令缺关键信息或安全约束，用模型模拟工具执行 | 最好的 agent（GPT-4 加安全提示）仍在 23.9% 的案例里不确认就执行了有风险的动作。从不行动的 NoAct 安全分满分，但有用性只有 0.063，所以安全分与有用性分开计 | 每个案例登记「规格缺了什么、哪些动作有风险、期望达成什么」，由评估器对照判轨迹；有用性单独打分，防止 agent 靠事事请示拿高分 | 对应换路线时的 `human: true`：该升级时不升级是失败，事事都升级也是失败，两者要分开计分。它的输入是合成指令，数值不能外推到 reviewer |
| τ-bench（[arXiv 2406.12045](https://arxiv.org/abs/2406.12045)） | 上下文 / 授权 | 模拟用户与带领域政策文档的客服 agent 多轮对话，按结束时的数据库状态判对错 | gpt-4o 单次成功率在零售约 61%、航空约 35%；8 次全成功（pass^8）在零售不到 25% | 同一输入跑 k 次，按全部成功计（pass^k），衡量稳定性而不是碰巧做对 | 只借 pass^k：每个重建案例跑多次，「至少一次漏」才算 base 复现，与 J 的门槛一致 |
| J 的评测方法对照（[本仓](correction-replay.md#评测方法对照)） | 本仓既有 | 从真实失败重建留出任务，在违反前截断，去掉纠正原话 | 研究对象是偏好遵循，不是方向排序或授权 | 截断点、去掉纠正、base 改前跑 2 次至少 1 次违反才跑改后 | 协议直接复用；它的遵循率读数不能当方向排序的证据 |

本轮检索到的公开工作里，没有一份测「评审的第一条意见是否指向路线问题」或「推荐换一类路线时是否交给 human」；上表的数值都是相邻任务上的结果，不作为本 Goal 的证据，本 Goal 的读数只能来自本仓的回放。

三条路径：

- 保留单轮合成夹具：base 已 4/4 先判方向，没有判别力，停用。
- 从真实失败重建（推荐）：#176 的三个误向案例来自本机项目落盘的 reviewer 记录，原始评审输入有可能找回。
- 等自然案例：不花回放预算，但只能看到 reviewer 在下一个真实误向案例上的表现，提供不了改前改后的对照。

三项观察怎么测：

- 第一条意见：截断点是批准误向 task 的那次 `plan-review` 调用之前。输入只给当时 reviewer 能读到的内容：那个 revision 的 plan、`task.md` 及链接文件。后来的实验结果、human 的纠偏、事后的方向评审与之后的 revision 都不给。human 的纠偏只作参考答案，交给判定方，判第一条 `must` 是否指向它。
- 换路线的 `human: true`：用「推荐换成零改动脚本」那个真实案例，分两步计：先计 reviewer 是否推荐换路线，被引出的次数里再计是否标了 `human: true`。没被引出就不计分，与 M3 相同。
- 误触发：对照组取同一批项目里方向事后被 human 确认对的 task，用同样的截断规则；计第一条 `must` 误报方向问题的次数和多余的 `human: true`，并核对原先被采纳的细节 `must` 是否仍被报出。这一条对应 CriticGPT 的误报计数与 ToolEmu 的有用性分。

判定沿用 J 的门槛：每个误向案例 base 跑 2 次，至少 1 次漏掉方向，才写改后措辞并跑改后。base 全部照做，就记为真实输入下也复现不出，D 回到等自然案例。重建材料含私有项目内容，只在本地使用，公开 PR 只写方法与读数。

**下一动作：** 不调用模型，先盘点 #176 三个误向案例与至少三个对照案例能否找回原始评审输入（那次调用时的 plan revision、`task.md`、链接文件与 review 记录）。误向案例找回 ≥ 2 个，就把重建回放写成下一个 task，先跑 base；不足 2 个，D 等自然案例。要不要给 Harness 加评审输入快照来留住今后的案例，属于 scope 取舍，交 human。

## 边界

- 结论只覆盖单轮、输入齐全的合成夹具。#176 的真实失败出在已有多份长文档的项目里，单轮夹具复现不出这类失败在本仓库已是第五次。
- M3 这一项（换路线是否标 `human: true`）没有被引出，现行措辞在这一点上未经检验。
- #176 评论里的第三条路径（`when-to-stop` 要求的临时评审，prompt 由 agent 自己写）没有回放。
