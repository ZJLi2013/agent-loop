# Case：RoboJEV × Nox-4B，一天 11 个 task 边界上的跨模型纠偏

> 时间：2026-09-24 一天。执行：Cursor 里的 Opus 5 + agent-loop；复核：gpt-6（Codex，读写同一批文件）；
> human 在两者之间搬运。硬件：单卡 MI300X，每个 task 预算 2 轮 / 2 小时 GPU。

## 结论

**执行层几乎不需要纠偏，决策层几乎每个 task 边界都被改写。** 11 个 task 边界里，7 次明确由 gpt-6
改写下一步，另 4 次改写没标来源、写法一致；Opus 5 每次都接受，没有一次提出反对证据。改写集中在四类：
纠正执行者写下的结论、改验收口径、拆开混在一起的变量、预先写死停止规则。

改写的效果是可见的：e9 按 gpt-6 的设计把留出集动作题全对率从 18.7% 提到 90.7%，闭环第一次对准并
下降到抓取位置；e13 预设了「失败即结束本轮」，本轮 Nox 请求适配按规则在 e13 停下，没有继续加闭环。

这说明 agent-loop 缺一个 **task 边界上独立于执行者的决策者**。当前由 human 手工充当这条通道，
形态与改法见文末。

## Goal 与分工

Goal：让 RoboJEV（[lykycy123/RoboJEV](https://github.com/lykycy123/RoboJEV)）的 pick & place 在
vLLM-SR Decision 模型 Nox-4B 上跑通；跑不通时把失败定位到具体决策阶段、请求或模型行为。

实际运转的环：

```text
Opus 5 执行 task ─► 写结论 + 提下一步
                        │
          human 复制给 gpt-6 ─► gpt-6 改 task.md / plan / 直接给文字建议
                        │
          human 贴回：「gpt-6 的建议，合适就采纳，然后继续 agent-loop」
                        │
          Opus 5 读更新后的 task.md ─► 同意 ─► 执行下一 task
```

## 逐轮记录

每轮三项：Opus 5 的提案、改写内容、执行结果。标 ★ 的是 human 明确注明来自 gpt-6 的。

**R1 ★ 11:20 — d 系列：demo 在 Nox-4B 上第 85 步失败之后**
- 提案：d2（原样接入）第 85 步把唯一可用的 `close_gripper` 选成 `open_gripper`，d3（三种候选描述）最好
  7/8，预算用尽；建议下一步改成 8 道独立 Noul 题。
- 改写：
  - 纠正结论：失败是模型违反可用动作约束、客户端执行前中止，不是物理松爪；
  - 纠正历史总结：semantic 描述能选对 close，但让另外四种状态选错，不能认定 open/close 固定反转；
  - 拆成两条路径：先修原始判断（direct 与 HTTP 对照、重排、匿名标签、task 消融、逐动作 Noul），
    或先用代码掩码保证闭环（单独记录，不算模型通过）；
  - 指出 `check` 在失败视频存在时仍返回 0，列为修复项。
- 结果：d4–d7 定位到 task 这句话是主要干扰（36 个状态原样 31/36，中性 task 36/36）；逐动作 Noul
  闭环 117 步 SUCCESS；`check` 的假通过修掉。代码掩码路径未采用。

**R2 ★ 14:05 — e1–e3：接入 RoboJEV 原生 Choice**
- 提案：Opus 5 写的 e1–e3 草案。
- 改写：gpt-6 更新 task.md；human 补一条验收口径：首阶段拿到「可信的原生 Choice 基线和可定位的失败」，
  不以高成功率为验收。
- 结果：e3 基线 0/10，失败定位到动作阶段（意图对、动作错）。

**R3 ★ 15:15 — e4：离线定位动作阶段**
- 提案：5 个变体 × 约 330 个状态，加 Qwen3-VL-8B 对照，带一条 50% 门槛和「Qwen 也低就停」的规则。
- 改写：
  - 直接复用 e3 日志里的原始请求，抽样重建比对，先原样重放再消融；
  - 单变量、不累计，补一个拆请求变体；
  - 加读字段探针，把「读不到」和「用不对」分开；
  - 删掉随意的 50% 门槛；纠正「意图 99.9%」的适用范围，以及对 Qwen 对照的过度归因。
- 结果：重放 592/592 一致；Nox 读字段 100%；夹爪错误归因到 task（0.7% → 99.3%）；x/y 错误归因到
  两条候选描述几乎逐字相同、模型按位置选。

**R4 ★ 16:00 — e5：改写轴候选描述**
- 提案：至少两种写法重写候选，再与「去 task」组合。
- 改写：
  - 两种写法各检验一个假设（区分信息的位置 / 条件组合表达），不同时大改；
  - 保留 zero 与 z 的原语义，客户端不预先算答案；
  - 6 × 2 完整矩阵，补 z 指标：z 的参考答案 143/148 是 zero，96.6% 的 z 正确率本身说明不了什么；
  - 148 个状态作开发集，冻结后在留出集检查一次；
  - 收紧一条记录：拆请求后 y 52.0% → 52.7%、翻转 1.4%，只能写「无实质改善」，不能写「已排除」。
- 结果：两种写法都没提升轴方向，改善全部来自去 task；非 zero 的 z 为 0/5。

**R5 16:50 — e7：只删动作阶段 task 的单种子闭环**
- 改写：human 更新了 task.md，写入一条停止规则：若只重现水平摆动，诊断到此结束，不再恢复 5 回合测试。
- 结果：200 步未成功；夹爪 100% 正确、空抓 0；水平方向反转 93 次，从未对准。按规则停。

**R6 ★ 17:32 — e8：原计划直接修，改为先做字段干预**
- 提案：直接进入修复（单分支候选 / 删 target 字段）并跑闭环。
- 改写：先做因果检验。固定意图与有效字段，只改不适用分支的字段，正倒序都测，标为离线条件遵循测试；
  报告措辞降一级，从「证明」改为「强烈支持，待干预确认」。
- 结果：不适用字段改变答案的比例 approach 组 67%、carry 组 55%，因果成立；这组数成了 e9 的闸门基线。

**R7 ★ 17:47 — e9：按意图简化 x/y 候选**
- 提案：三种条件并测：单分支、单分支 + 删 target 字段、带 / 不带 task。
- 改写：
  - 主实验只改候选、保留完整 state；删字段降为次要消融，因为它同时影响同请求的其他题，解释不干净；
  - 补齐 2 × 2 的 task 对照：plan 的「下一步决策」与 e9 设计写法不一致，照原样会漏基线；
  - 验收除准确率门槛外再看五条：干扰是否消失、正倒序、三类方向、留出集、有无退化；
  - e8 干预集补上相反方向和 zero，避免只对某个符号成立的方案。
- 结果：五条闸门全过；留出集全对率 18.7% → 90.7%；干扰比例 67% → 22%、55% → 13%；闭环第 29 步
  首次对准、第 91 步下降到抓取高度、方向反转 0 次，但仍未抓起。本轮最有效的一次改写。

**R8 ★ 19:01 — e10 / e11：卡在抓取那一刻**
- 提案：z 也改单分支；单独诊断意图题。
- 改写：
  - 读第 91 步的真实请求，拆出两个独立错误：意图没切到 grasp，z 越过抓取位置；只修一个未必能抓起；
  - z 单分支必须保留「未对齐不下降」的门控，按四类行为分别验收，不让大量 zero 样本掩盖失败；
  - 意图诊断带上抓取边界前后的负例，用规则 rollout 做跨来源检查；
  - 不写 `if grasp 全为 zero: intent = grasp`：它把要检验的能力交给了规则；
  - 列出闭环入口条件。
- 结果：e10「到位停止」不过；e11 显示意图几乎不选 grasp，候选顺序是主导因素；e12 入口不满足。

**R9 19:19 — e13：收敛到一次预设模板**
- 提案：一套新问法（状态分类 Choice + 固定映射），附两个待 human 决定的问题。
- 改写：
  - z 写成分段规则，候选只留 negative / zero / positive；
  - 意图只做局部 Noul 诊断；
  - 只预设这两套模板，不再搜索措辞；
  - 预写结论规则：任一项失败，就结束本轮 Nox 请求适配，转其他模型或回归用例，不再加闭环。
- 结果：两项都差一点未过：z 正序四类全对，倒序「未对齐」68%，低于 80% 门槛。按规则结束本轮，e12 取消。
  Noul 的「抓取就绪」判断在所有正负例上 100% 正确，成为下一轮的起点。

**R10 19:31 — 本轮结论的措辞**
- 改写：「同一组事实与规则，写成 Noul 局部谓词判断时正确；写成带动作标签的 Choice 时，条件遵循不稳定」，
  并限定适用范围为本轮测过的模型版本、请求与状态集。
- 结果：Opus 5 回复「这个表述比我前面的说法更准确」，readme 结论按此改写。

**R11 19:37 — r7：换成 model + runtime co-design**
- 改写：plan 与 task.md 由另一侧改写为 r7：模型只判局部谓词，runtime 按决策表组合意图，
  动作由代码执行；用同一 runtime 的纯代码谓词路径作对照；e14 离线冻结 → e15 单种子对照 →
  e16 新种子泛化，每步过关才进下一步。
- 结果：e14 开始时宿主工具连续失败，尚未执行。

## 改写落在哪四类

| 类别 | 轮次 |
|---|---|
| 纠正执行者写下的结论或措辞 | R1、R3、R4、R6、R10 |
| 改验收口径 | R2、R4、R7、R8 |
| 拆开混在一起的变量 / 补缺失的对照 | R1、R3、R4、R6、R7、R8 |
| 预先写死停止规则 | R5、R8、R9、R11 |

第一类说明，复核者必须读原始证据：R1 的「历史总结有误」、R4 的 z 基准率陷阱，只读执行者的摘要都发现不了。

## 执行者一侧的模式

- **接受率 11/11。** Opus 5 没有一次以事实反驳，多次主动承认原提案更弱（「采纳，这比我原来的更干净」）。
  「同意」在这里零信息。
- **提案倾向于加选项。** R7 在主实验里混入会污染其他题的删字段条件；R9 提出一套新问法并反问 human；
  e11 后给出三个方向让 human 选。改写的方向相反：砍条件、加闸门、写停止规则。
- **执行质量本身没被质疑。** 脚本、重放一致性、日志落盘、闭环录像，11 轮里没有一条改写针对执行。

## 暴露的 agent-loop 问题

- **human 是唯一的决策通道。** 每轮靠复制粘贴，审批语义是「合适就采纳」，Harness 里没有任何记录
  说明下一步由谁批准。
- **Goal Review pause 让 verify 以 `runner is paused` 拒绝执行**，项目包装脚本的输出里却混着上一次的
  artifact，要再查一次状态才分得清本次有没有跑（e1）。
- **双 agent 共用工作树时 fingerprint 崩溃。** `workspace_fingerprint` 读到另一个 agent 在 `.codex/tmp/`
  下的临时文件（WinError 1920），verify 两次崩溃，结果只能以 verifier 的原始输出为准（d7）。
- **Harness disable 后 runner 拒绝执行**，补充测量只能绕过 runner 直接跑（d8）。
- **结论落点被 human 纠正了两次。** 关键事实与结论要沉淀到项目文档（readme / exp 记录），
  `task.md` 与 `.agent-loop/` 只放可随时删改的状态。
- **工作文件没有版本历史。** 项目目录未提交，任何一轮改写前的 task / plan 状态只能从会话记录还原。

## 由此推出的形态

把 human 手工做的这一步变成 Harness 的一段：

```text
Opus 5 执行 task ─► 结束：VERIFIED / 重试用尽 / 假设被推翻
  └─► close 报告（结论 + 原始证据路径 + 候选下一步）
        └─► Harness pause（kind=planner_review），commit 当前 task / plan
              └─► planner（新上下文，只读文件）─► 决策文件 + 改写 task.md 下 1–2 行
                    └─► Opus 5 只做事实核对 ── 有错 ─► 退回一次 ─► 仍分歧 ─► 问 human
                          └─► resume：校验决策绑定当前 rN 与证据指纹
```

- **输入**给原始证据，不给执行者的对话；新上下文本身是收益的一部分。
- **输出**绑定 revision：`continue | replan | stop | ask_human`、结论修正、下一 task 的
  pass / fail_to / budget、一句「为什么推进 Goal」。
- **否决**只接受事实错误（路径、数字、已做过、跑不了、超预算），不接受偏好。
- **Goal / scope 变化**（如 R11 的 r6 → r7）仍由 human 批准。

**第一步是 replay，而不是接入：** 把本文 11 轮改写前的状态交给新上下文的 Opus 5，看它能独立复现多少改写。
多数能复现，planner 就用新上下文的 Opus 5；多数不能，再接 Codex 用 gpt-6。两种结果的角色拆分、
契约与 guard 相同，replay 只决定 driver。
